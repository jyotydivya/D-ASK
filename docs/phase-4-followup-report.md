# Phase 4 follow-up: planner fixes, verification integrity, and the 0.5B / 1.5B / 3B benchmark

Date: 2026-11-03. Machine: i5-1335U, 15.7 GB RAM, Iris Xe GPU. Inference: llama.cpp b11720 with Vulkan, temperature 0, 4096-token context.

Every number below comes from the result files in `research/benchmark/results/` and is regenerated by `npx tsx research/benchmark/report.ts`, which writes `research/benchmark/RESULTS.md`. Numbers are labelled **measured**; anything else is labelled **hypothesis**.

## 1. What changed

### Planner and runtime (product)

**Runtime-generated dependencies**
- The model no longer writes `dependsOn`; it isn't in the model's output schema.
- The runtime makes every step depend on the previous one, so a failed step stops all later steps (fail-closed).
- Dependency errors from an unconstrained model are rejected with an explicit error, never dropped silently: a step that depends on itself, on a later step, or on a step that doesn't exist (which covers cycles).
- Inputs that try to use another step's result are rejected the same way, for example `{{s1.output}}`, `s1.result` or `result.time.split(...)`.

**Request-derived argument domains** (fixes the two planner defects from the Wi-Fi-off run)

| Tool | Argument | Rule |
|---|---|---|
| `system.time` | `timeZone` | Forbidden unless the request names a zone or city, so local time is used. Otherwise restricted to the IANA zones for the named places, looked up in the runtime's own tz database. |
| `math.evaluate` | `expression` | Must be one of the expressions written in the request, verbatim. Whitespace is ignored. |
| `workspace.list_dir` | `path` | Restricted to the folders named in the request. |

- **Expression handling:** parentheses and precedence are preserved. Implicit multiplication becomes explicit, leading unary minus is kept, and spoken operators and typographic symbols such as `×` are normalised.
- **Enforcement:** the domains are applied in three places: the output grammar, the planner prompt and plan validation, and a hard check immediately before each tool call.

**Experimental switches separated from defaults**
- `experimental.planGrounding` and `experimental.gapReplanning` are both **off** by default.
- `argumentConstraints` is on (product).
- Fail-closed completion verification is always on and has no switch.

### Completion verification (fail-closed, always on)
`completed` requires all of the following:
- every step succeeded;
- every step is grounded in the request;
- every request part detected deterministically is covered by real tool output;
- **(new)** every content word of the request is explained by a detector that fired;
- the model's assessment agrees. The model can only downgrade.

The new condition fixes a defect the v2 benchmark found. "Search the web for today's weather forecast" was `completed` by 1.5B, because "today" triggered the time check and a time lookup covered it. That task is now `unverified`, with "search, web, weather, forecast" listed as unexplained.

- **Regression case added:** "Is it morning or evening for me right now?" (Phase 4 task p05) is now recognised as a local-time request.

### Tests

**Updated expectations** (behaviour changed on purpose)

| Test | What changed |
|---|---|
| E6 | Sequential dependencies: a failed step now skips the later independent step. |
| E11 | The step after a denied approval is now skipped. |
| E12 | Split into two plans, so both its checks still run. |
| S2, V1, V2 | `dependsOn` is no longer in the model schema. |
| Y1, Y2, Z1, Z5 | Rejection message wording; experimental switches now set explicitly. |

**New grounding tests**

| Group | Covers |
|---|---|
| D1–D7 | Self-dependency, cycles, forward references, valid multi-step plans, cross-step data references |
| T1–T6 | Timezone resolution, including the morning/evening regression |
| P1–P13 | Parentheses, nested expressions, precedence, unary minus, implicit multiplication, equivalence up to whitespace, rejection of value-equal rewrites |
| W1–W4 | Whole-request explanation, including the u04 regression |

**Offline integration test**
- It now reports infrastructure (N0–N5) and functional results separately.
- Reaching a terminal state no longer counts as success: a task passes only if the tool output proves it was served and it was reported `completed`.

## 3. Benchmark

### 3.1 Which switch helps (v2 code, 36 tasks, paired against the product configuration of the same model)
Measured.

| Model | Variant | Success (variant / product) | Wins / losses | Exact sign test p |
|---|---|---|---|---|
| 0.5B | argument domains **off** | 12 / 22 | 0 / 10 | 0.002 |
| 0.5B | planGrounding on | 22 / 22 | 0 / 0 | 1.0 |
| 0.5B | gapReplanning on | 22 / 22 | 0 / 0 | 1.0 |
| 1.5B | argument domains **off** | 16 / 20 | 2 / 6 | 0.29 |
| 1.5B | planGrounding on | 20 / 20 | 0 / 0 | 1.0 |
| 1.5B | gapReplanning on | 21 / 20 | 1 / 0 | 1.0 |

- **Argument domains:** clearly help 0.5B, and the direction is the same for 1.5B, though not significant at n = 36. They stay **on**.
- **planGrounding and gapReplanning:** no measurable benefit once argument domains exist. Both stay **off**.

**Phase 4 code vs v2 code, 0.5B** (not paired: code and switches differ). Task success rose from 8–10/36 to 22/36. First plans that passed validation rose from 33–44% to 100%. Self-dependency, previously the most common rejection (44× in Phase 4), can no longer occur.

**Output schema ablation** (v2, product configuration, measured)

| Model | Task success without schema | With schema | First plan valid without schema |
|---|---|---|---|
| 0.5B | 0/36 | 22/36 | 8% |
| 1.5B | 20/36 | 20/36 | 78% |

Grammar-constrained output is essential for 0.5B.

**CPU vs Vulkan** (v2, product configuration, measured)
- **Quality:** similar (0.5B 20 vs 22/36; 1.5B 20 vs 20/36).
- **Speed:** Vulkan is faster: 0.5B median 3.9 s vs 8.2 s; 1.5B median 5.7 s vs 14.1 s, 95th percentile 20.2 s vs 40.8 s.
- **Memory:** for 1.5B, the `llama-server` working set on CPU was 1,816 MB vs 1,419 MB on Vulkan.

**Determinism:** the 1.5B repeat run gave an identical outcome on 36/36 tasks.

## 5. Model recommendation
Measured basis, with the recommendation as a hypothesis.

- **1.5B shows no measurable quality advantage over 0.5B on this suite** (20 vs 22 of 36; intervals overlap almost completely), at twice the RAM and about twice the latency. Its only edge is robustness without the output schema.
- **3B is the strongest** on success (27/36), multi-step (4/6) and refusals (3/5), and its own assessment made no false claims even under the legacy rule. It costs 2.4 GB of working set and about 15 s median latency, and it needs roughly 4.6 GB free RAM to be admitted.
- **Recommendation (hypothesis to test next):** keep 0.5B as the default and fallback. Add memory-aware model selection that uses 3B when the guard admits it. Drop 1.5B as a candidate unless a broader suite shows a benefit.

## 6. Research claim (provisional)

**Measured, on this suite only (36 tasks, 4 read-only tools, one author):**
- **Argument domains:** request-derived argument domains, enforced in decoding and before execution, improved 0.5B task success from 12 to 22 of 36 (paired, p ≈ 0.002).
- **Fail-closed verification:** deterministic, whole-request verification brought incorrect completion claims from 30–33% (legacy rule: 9/30 for 0.5B, 8/24 for 1.5B) to 0 for every model tested.
- **The cost of being fail-closed:** 4–8 correct answers per model were not marked `completed`.

**Not established:**
- **Generality:** whether this generalises beyond four simple read-only tools, or to requests whose arguments aren't written literally in the text.
- **Prior art:** whether it improves on existing approaches. Nothing was compared against established baselines: grammar-constrained decoding alone, LLM-as-judge or self-verification with a stronger judge, ReAct-style re-planning, or execution-based verification from the tool-use literature. No literature review has been done, and related prior art very likely exists. **Novelty must not be claimed yet.**
- **Bias:** the detectors, tasks and oracle share one author, despite the code separation.

**Needed to make this a research contribution:**
- an externally written task set with broader tools;
- the baselines listed above;
- several seeds or temperatures;
- a literature review;
- the false-claim and missed-completion trade-off reported as a curve, not a single point.

## 7. Recommended next milestone
**Phase 5: the stdio agent host**, as already specified: a versioned JSONL protocol, cancellation and Emergency Stop within 500 ms, no network listener. Two measured items from this work should be folded in:

1. **Pre-execution capability check (measured experiment).**
   - **Idea:** use the same unexplained-word analysis *before* planning, so requests that no tool explains are declined up front ("I can't search the web") instead of running unrelated tools.
   - **Why:** this targets the 0/5 refusal rate of 0.5B and 1.5B.
   - **Before turning it on:** measure the cost on paraphrased requests, and keep it off by default until measured.
2. **Memory-aware model tiers:** 3B when admitted, 0.5B fallback, using the existing supervisor and guard unchanged.

**Separately, for Phase 6:** re-measure "≥1 GB free with HUD + daemon + agent" once the HUD hosts the agent.
